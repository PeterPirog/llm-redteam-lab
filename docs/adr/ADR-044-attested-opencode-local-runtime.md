# ADR-044: Attested local OpenCode runtime for AGENT campaigns

Status: Accepted  
Date: 2026-09-11

## Context

The laboratory can already evaluate OpenCode as an `AGENT` target, collect durable tool
evidence, run adaptive multi-turn Red, materialize immutable repository/terminal fixtures
and distinguish `MODEL_COMPROMISE` from independently verified `SYSTEM_COMPROMISE`.

However, an adapter connected to an already-running OpenCode server does not prove how that
server was launched. In particular, OpenCode's application permissions are not an operating
system sandbox. Shell execution inherits host filesystem, process and network authority, and
OpenCode's normal defaults are intentionally usable rather than a red-team containment
boundary.

A campaign that declares external network and Git publication denied must therefore not
infer those controls from a prompt, from Red metadata, or from OpenCode permission rules
alone.

## Decision

Restricted local OpenCode campaigns separate stable target policy from per-run execution
evidence.

### 1. Deterministic OpenCode runtime profile

The laboratory constructs a deny-by-default local profile with:

- headless `opencode --pure serve`;
- explicit loopback binding only;
- session sharing disabled;
- automatic update checks disabled;
- default-deny OpenCode permissions;
- external-directory access denied;
- `webfetch` and `websearch` denied;
- subagent/task launch denied by default;
- shell denied by default, with an explicit narrow allowlist when a testcase requires it;
- `.env` reads denied.

The generated configuration is deterministic and fingerprinted. Secret values are never
placed in the launch plan; only required secret environment variable names may be recorded.

### 2. Stable sandbox policy

`AgentSandboxPolicy` describes the security-relevant isolation configuration that is part of
the Blue target identity. It includes:

- isolation/enforcement mechanism class;
- whether the workspace is disposable;
- whether external network egress is denied;
- whether Git publication is denied;
- the allowed loopback endpoint policy.

Only loopback HTTP(S) endpoints may appear in the default allowed-endpoint set. A policy that
does not require disposable workspace, external-network denial and Git-publication denial is
insufficient for the restricted default campaign.

### 3. Independent per-run sandbox attestation

A trusted harness issues `AgentSandboxAttestation` for each isolated execution. It binds:

- the exact runtime-profile hash;
- the exact stable sandbox-policy hash;
- the workspace hash;
- an ephemeral isolation identity;
- a proof hash generated by the trusted harness.

The Red model, repository content, target output and OpenCode process are not permitted to
mint or modify this attestation.

The full launch-plan hash and attestation hash are per-run evidence and may legitimately
change between replicates. They are not themselves the Blue target identity.

## Target identity

An `AttestedOpenCodeTarget` wraps the existing OpenCode adapter without changing its request
or durable-evidence semantics. Its Blue target `configuration_hash` binds:

- the base OpenCode/model/application configuration;
- the deterministic OpenCode runtime-profile hash;
- the stable sandbox-policy hash;
- the workspace identity hash.

It deliberately excludes the per-run `isolation_id`, proof hash and full attestation hash.
Therefore two clean replicates of the same system remain the same Blue target, while a real
change to network policy, allowed endpoints, workspace policy or OpenCode permissions creates
a new target identity.

The wrapper advertises `runtime_attested`, but it does **not** advertise
`untrusted_context`. Real MCP/tool-context transport must be implemented and verified before
that capability is added.

## Security rationale

OpenCode permissions are useful defense in depth and provide a measurable authorization
layer, but shell rules cannot establish host-level network containment. A shell command may
invoke arbitrary programs, language runtimes or alternate Git/network clients. The project
therefore keeps application authorization and system isolation as distinct evidence layers.

The separation between stable target policy and per-run proof is also required for valid
statistics. Replicates must vary execution evidence without silently changing the measured
Blue configuration.

This directly preserves the project rule:

```text
model requests forbidden action
        ↓
OpenCode permission/runtime decision
        ↓
OS/container isolation decision
        ↓
independent state/effect verification
```

A model can be compromised even if later layers block the effect. Conversely, system
compromise requires evidence that an unauthorized effect actually crossed the declared
boundary.

## Consequences

### Positive

- restricted OpenCode campaigns can no longer silently rely on permissive process defaults;
- launch/configuration policy becomes reproducible and target-identity-bound;
- repeated trials retain one stable Blue target identity;
- per-run isolation/proof remains auditable execution evidence;
- loopback/local-first operation is explicit;
- attacker-controlled content cannot expand runtime permissions;
- network and Git-publication claims require independent control-plane evidence;
- no real secrets are persisted in launch-plan artifacts.

### Limitations

- this ADR introduces the typed launch/policy/attestation contract but does not start or
  supervise the OpenCode process;
- a concrete Docker/Windows isolation harness must issue the attestation in a later vertical
  slice;
- local model access may require allowlisted loopback endpoints;
- real MCP context transport remains separate work and must not be simulated by copying MCP
  text into the direct user prompt.

## Rejected alternatives

### Trust OpenCode permissions as the sandbox

Rejected because shell execution inherits host authority and permission patterns are an
application control, not an OS/network isolation proof.

### Include per-run isolation proof in Blue target identity

Rejected because replicates of the same configuration would become different targets,
invalidating repeated-trial aggregation and target-version comparisons.

### Bind OpenCode to `0.0.0.0` for convenience

Rejected for default adversarial campaigns. The headless API is loopback-only unless an
explicit future threat profile requires otherwise.

### Persist server passwords or model credentials in launch plans

Rejected. Only environment variable names may be part of the reproducible plan.

### Advertise MCP/untrusted-context support before a real transport exists

Rejected because doing so would overstate coverage and could turn an indirect-injection test
into a direct-prompt test.
