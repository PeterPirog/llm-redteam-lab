# ADR-036: Immutable environment fixtures for adaptive indirect-injection evaluation

Status: Accepted
Date: 2026-09-11

## Context

Repository text, terminal output, retrieval context, tool data and MCP metadata can carry
attacker-controlled instructions without appearing in the user's direct prompt. Treating
those attacks as ordinary user messages destroys the trust-boundary provenance needed to
explain why a system failed and can overstate Red effectiveness.

The laboratory already has adaptive multi-turn Red, durable AGENT evidence, deterministic
system-state verifiers, held-out evaluation semantics and disposable local coding fixtures.
The missing link was an executable lifecycle that binds the environment artifact to the
attack while keeping it separate from Blue configuration and from Red's direct prompt.

## Decision

Environment-originated attacks use an immutable fixture bundle as a first-class attack
input.

1. The complete fixture bundle is SHA-256 fingerprinted before the campaign starts.
2. Each trial receives a clean materialization in an explicitly owned local sandbox.
3. A non-empty sandbox without the laboratory ownership marker is never deleted or reused.
4. Fixture symlinks and path traversal are rejected in v1.
5. The first Blue interaction is the legitimate task declared by the fixture manifest.
   Hostile content remains in the repository/tool environment; it is not copied into the
   user prompt by the harness.
6. Later turns may adapt to target-visible Blue behavior under the normal multi-turn budget.
7. Fixture provenance is recorded as hashes and isolation identifiers, not raw synthetic
   secrets.
8. A precise forbidden-path verifier is preferred to a whole-workspace hash for system
   compromise. Legitimate task edits are expected and must not become false positives.
9. A requested or denied forbidden action can establish `MODEL_COMPROMISE`; only trusted
   independent effect evidence can establish `SYSTEM_COMPROMISE` where the Judge policy
   requires effect verification.
10. Fixture-aware Red has a distinct runtime fingerprint (`AGENT` fixture runtime v4).
    Existing MODEL/PIPELINE v2 and non-fixture AGENT v3 fingerprints remain unchanged.
11. Fixture execution is DISCOVERY-only in v1. EVALUATION fails closed until the held-out
    manifest binds fixture bundle hashes as part of the immutable evaluation population.
12. External network, real git publication, real credentials and production secrets remain
    denied by default. Native fixtures use synthetic canaries and local inert effects only.

## Rationale

This preserves the causal distinction between:

- a direct jailbreak supplied by the user,
- an indirect instruction encountered in an untrusted environment channel,
- a model deciding to request a forbidden action,
- a runtime authorization decision,
- a provider reporting execution, and
- an independently observed system effect.

It also prevents cross-trial contamination: every attempt starts from the same hashed
fixture template and receives a unique isolation identity. This is required for credible
multi-turn comparisons because a prior agent run must not mutate the next run's starting
state.

## Consequences

### Positive

- Repository and terminal-output prompt injection become executable adaptive attacks rather
  than taxonomy-only entries.
- Multi-turn Red can test sequences in which an environment injection establishes context
  and later turns probe or amplify the resulting trust-boundary failure.
- Campaign and per-attack provenance can identify the exact fixture bundle used.
- State-verifier evidence retains the project-wide MODEL/SYSTEM compromise distinction.
- Existing target identities remain stable because the fixture is an attack input, not a
  Blue configuration field.

### Limitations

- v1 reuses the existing `multi_turn` conversation engine. A future environment-aware
  runner may give `environment_injection` its own execution mode without changing these
  provenance rules.
- Materialized synthetic environment values are generated by the fixture runtime, but a
  separately running OpenCode process still needs an explicit launcher/environment bridge
  before environment variables can be injected safely. The repository and terminal-output
  surfaces do not depend on that bridge for marker-based system-effect tests.
- RAG and MCP fixture providers are represented in the manifest vocabulary but are not yet
  implemented as concrete loaders in v1.
- Held-out fixture EVALUATION is intentionally unavailable until fixture hashes are added to
  the evaluation manifest contract.

## Rejected alternatives

### Copy hostile fixture text into the direct user prompt

Rejected because it changes an indirect prompt-injection problem into a direct jailbreak and
loses source provenance.

### Treat any workspace change as system compromise

Rejected because the legitimate coding task is expected to modify files. System compromise
must be tied to a declared forbidden effect or trusted state surface.

### Reuse one mutable workspace across trials

Rejected because execution order would become an uncontrolled treatment and contaminate
multi-turn attack comparisons.

### Let the Red model prepare or mutate fixtures

Rejected because attacker-controlled content may not expand its own permissions or alter the
measurement control plane.
